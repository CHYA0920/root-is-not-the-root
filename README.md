# 内核生命周期之外

> 一台研究设备上的长期实验。
> 本仓库不是教程，不是工具，也不是漏洞报告。

---

## 一、这个项目在找什么

先说结论，再说过程。

今天几乎所有"拿到设备控制权"的方案，都停在同一层：**在系统已经跑起来之后，改这个系统正在运行的东西**。

改完是有效的——直到重启。

重启之后一切归零。于是所有人都在同一个循环里打转：找一个入口 → 进去 → 改一遍 → 重启 → 再找下一个入口。

这个项目从一开始就问了一个不太一样的问题：

**能不能不做这件事？**

能不能不去"改一个正在运行的系统"，而是**站到一个更高的位置上，主持这个系统怎么存在**？

这就是整个项目的方向。下面所有的架构、文档、工具、日志，都是从这一个问题里长出来的。

需要提前声明的是：本仓库只交付**概念、架构与判据**。抵达那个位置的具体路径不在本仓库范围内——包括本机的环境条件、取得的途径、以及设备型号。

## 二、实际在跑什么

不谈设计，先看东西。

这个实验在本机磁盘上的占用是 **11.7 GB**，**27,000 多个文件**。

按体量排下来是这样：

| 目录 | 体量 | 里面是什么 |
| --- | --- | --- |
| `test_build/` | ~2.2 GB | 构建产物堆积：历代内核模块、动态库、镜像包 |
| `test_logs/` | ~1.8 GB | 发射记录：**1,498 个轮次目录**，每轮一份自己的现场 |
| `Temp/` | ~555 MB | 临时与中间物（打包、反编译、依赖缓存） |
| `analysis/` | ~476 MB | 反编译输出、分析脚本、参照物 |
| `apk_liquid_glass/` | ~101 MB | 一个实验期的上位机界面工程 |
| `_legacy/` | ~63 MB | 早年被替换掉的实现，留着不删 |
| `artifacts/` | ~41 MB | 归档产物 |
| `vendor_mods/` | ~21 MB | 从设备固件中取出的第三方内核模块样本 |
| `physruntime/` | ~19 MB | 上机位运行时：构建、发射、判读、编排 |
| `docs/` | ~11 MB | 项目自己的文档体系 |
| 其余 | ～ | 交叉编译树、参照资料、哈希表等 |

文件类型也很能说明问题：

```
txt   14218      源码   2044       Python  1433
ko     1385      日志   1282       so       643
c       451      md      285       h        217
```

**14,218 个 txt、1,282 个日志文件**——这个项目最厚的部分不是代码，是**记录**。

原因很简单：这个方向上的每一步都不可逆。没有记录，就分不清「这次失败是因为改错了」还是「这次失败是因为前提变了」。到后来，记录本身成了基础设施。

## 三、发射是怎么跑的

这个项目给"跑一次实验"这件事专门建了一条流水线，名字叫**发射**。

一条完整的发射链大致是这样：

```
选节点配方 → 构建 → 打包 → 产物对账 → 推送到设备 → 重启取净环境 → 发射 → 抓回判据 → 机器判读
```

几个在实战里被逼出来的规矩：

**每次发射前无条件重启。** 不是"出问题了才重启"，而是**每一次都必须从干净前提开始**。因为上一轮的残留会让这一轮的结果无法归因。这一条是血换来的。

**判据必须能自证。** 每次发射前先跑一次判据通道自检——如果连"执行体在不在场"这件事都测不出来，后面的结论一律不算数。

**失败要分类。** 不是"成功/失败"两档，而是细分成好几种情形，每种对应不同的处置动作。分不清失败类型的轮次，视同没跑。

**结论不可采信也要写下来。** 有些轮次的环境本身就是坏的，结论不能用来判断任何事——这种轮次要被明确标成"不可采信"，而不是悄悄丢掉。

**一条硬闸门：连续三次打不中前提，自动停发。**

这条闸门救过很多次。人在连续失败之后会开始"微调参数再试一次"，而这个方向上的微调几乎都是无效劳动。闸门直接把人从循环里拽出来。

## 四、那些轮次目录里装着什么

每跑一轮，就产生一个以时间戳命名的目录。**现在有 1,498 个。**

一个典型轮次目录里的东西：

| 文件 | 作用 |
| --- | --- |
| `key.txt` / `key_fp.txt` | 会话凭据与凭据指纹（明文只落到这里，其余地方只记指纹） |
| `verdict.txt` | 这一轮的最终判决，一行 |
| `verdict.json` | 逐项判据的机械判读结果 |
| 若干现场文件 | 从设备上抓回来的运行现场 |

`verdict.txt` 是其中最有意思的一栏。这一栏不是一句"成功"或"失败"，而是一行带现场信息的短判决。

下面是从一千多个轮次里挑出来的几条（**仅作体量示意**）：

```
ALIVE
NOT-ALIVE
ALIVE (重放命中)
PARTIAL
FIRED (未装载 ×3, 无有效数据)
FIRED (环境劣化, 连续 3 次不可信, 结论不可采信)
FIRED (错过轮次 ×2, 设备已被触碰)
```

这几行之所以可以被挑出来，是因为**脱离上下文，这些判决什么也说明不了**：不知道在测什么、判据是什么、成功意味着什么、能不能复测、能不能复写。这正是可以给人看的那种记录。

反过来说：一千多个轮次里，绝大多数判决都比这具体得多——**那些不在这份文档里**。

**轮次的分布本身就是一份体检报告。** 粗略看一眼：

| 数量级 | 判决倾向 | 说明 |
| --- | --- | --- |
| 一百多条 | 前提命中，主体未通过 | 最常见的一类：打进去了，但目标没成立 |
| 几十条 | 主体成立但通道缺失 | "活着但叫不应" |
| 几十条 | 部分成立 | 半边通过 |
| 少量 | 打不中前提 | 连门都没进去 |
| 少量 | 环境不可信 | 这一轮的结论不能用 |

**最成功的判决反而最少。** 这就是研究工作的形状。

## 五、几段插曲

下面这些是路上真实发生过的事，讲出来比讲设计有意思。

### 东西被人删了

有一个阶段，项目已经做出能在设备上跑起来的产品了。

然后有一天，什么都没有了。

不是崩溃，也不是被人发现之后制止——是**静默地、毫无预告地被清除了**。当时那件东西的载体是一个内部测试用的虚拟现实应用，然后就什么都没有了。

事后复盘了好几轮，能确定的只有一件事：**把产品放在一个第三方随时能碰到的地方，等于没有产品。**

从那天起，"存在形式"本身就是设计的一部分。

### 攻击者不是内核，是自己写的代码

走了一段时间之后，挡在面前的既不是内核，也不是任何安全组件。

**是自己写的东西。**

当时的做法要求每一个功能都靠"在运行时动态改写内核代码"来实现。一个功能一次改写，十个功能十次改写。系统越来越脆，每一次改动都在给下一次埋雷。

扩展推到一半，工程价值被自己否决了。

那次挫折之后才想明白：**这个方向不能靠不断叠加技巧往前推。**技巧是可以被安全策略追着打的；要摆脱这种被动，必须换一个完全不同的位置。后来的那次层级跃升，就是从这里逼出来的。

### 自己成为内核的一部分

换位置之后的收获，比预想的大得多。

原先所有的做法都是"从外面操控一个正在运行的系统"。而当执行体不再以外来者的身份存在、而是成为**内核自己的一部分**时，一堆原先需要"斗"的问题突然不需要斗了：内核只对自己之外的程序做校验，对"自己"不做。

那一阶第一次接近了内核更底层的上下文。

但那一阶没有被急着往下推。因为上一阶已经摔过一年跟头——这次先把地基铺好：项目规范、文档体系、发射流程、测试协调、日志统计，全都从头自建了一遍。

**这些工具不是陪衬，是这一阶能继续往前走的唯一原因。**

### 一句话想反了两天

有段时间一直在琢磨：既然执行体已经在内核里了，那能不能就地触发一次内核自己的重启，重启完自己还在？

这个想法看起来很顺：让内核重启，而自己装作没被重启到。

结论是做不到。

原因说出来很简单：**内核重启时，内核自己的内存分配器会把全部内存收回。** 发起的一方即使"还在"，也已经被收回掉了——等价于**站在一栋正在被拆掉的房子里，指挥这栋房子重建**。

这个坑值得写下来，因为这个设想太顺了，顺到几乎每个人都会先走一遍。

### 数据不会骗人

到某个阶段，项目开始相信一件事：**不要相信印象，只相信记录。**

于是有了一个很朴素的做法——把每一次发射的判决都留档，不管成功、失败、还是不可采信。

后来发现，最有用的一栏不是"成功了多少次"，而是**"失败是怎么分类的"**。因为失败的类型会先于成功暴露方向是不是错了。

## 八、最后三句

**这不是验证报告。** 本仓库的一切是理论设计与架构描述，并且仍在研究中。文档不给操作步骤、不给参数、不给实现载体，也不给任何可以被直接照抄的内容。

**一切结论以那台设备为准。** 文中出现的每一条硬件事实，对象都是那台实验设备。换个平台，结论需要重新验证。

**这是一条真实的边界。** 这个方向不碰磁盘，不碰固件，不进入硬件安全层。最坏的结果是**一切归零**，而不是设备损坏。

这也是本仓库愿意把过程写出来的原因之一：**能说清楚边界的方向，才值得往下走。**
